# Curated directory identities and review

`app/src/utils/directorySchema.ts` is shared by rendering, form proposals, recovery tooling and the data validation command. Business records retain their existing display fields and have an immutable `businessId`; names, URLs, state sets and classification can change without changing that ID.

`legacy-place-identities.json` assigns immutable `locationId` values to the legacy place IDs. It stores associations only, with unknown historical verification recorded as null. Coordinates, addresses and scores remain in the unchanged legacy snapshot. Duplicate snapshot branches share one location identity. Ambiguous historical associations retain their candidates until an independently sourced reviewed location resolves them.

`reviewed-places.json` holds branch details linked to each business by `businessId`. A branch needs a unique `locationId`, name, AU state/country, cafe status, a source URL and actual review time. Supply a sourced street address, a confirmed Google `placeId`, or both. A rating-only record can instead identify the reviewed listing with a specific Google Maps/review link in `source.url`. The business website is derived automatically.

## Fill in a submission

The submission PR already creates the business entry. To add an address, rating or marker, copy [`PR-submission-template.json`](../PR-submission-template.json), fill it in, and paste the **whole object** into the array in `app/src/data/reviewed-places.json`. For an existing branch, update its entry instead of appending a duplicate. Bean Junction's business ID and basic details are prefilled in this branch's template. Its reviewed 4.5 score and Google review source are recorded in the data; its address, place ID and coordinates remain unknown.

- Keep the PR's `businessId`. Give each branch a unique `loc-...` ID, or preserve its existing ID. Set `hasCafe` for that branch; a roastery without a cafe can still have an address, rating and marker. Also review the business-level cafe flag in the PR if it needs correcting.
- Fill `address` as `street, locality STATE postcode, Australia`. Omit an unknown postcode. If only a confirmed place ID is available, remove `address` rather than keeping a placeholder.
- Enter the branch's reviewed Google Maps score in `rating` (a number from 1 to 5), or leave it `null` for unknown. A rating does not require coordinates or cafe access. If no address or place ID is available, use the specific Google listing/review link in `source.url` (a Maps place/share link, CID link, or Google Search URL with its `#lrd=...` review fragment). A generic search URL or business homepage is insufficient for a rating-only record. The listing keeps its Online label, and its stars link to the supplied review source without creating a marker. Scores stay attached to their branch; the highest branch score is used for directory sorting. An explicit `null` clears an older score for that branch.
- For a static map marker, fill a confirmed `placeId` **and both** numeric `latitude` and `longitude`. Otherwise leave those optional fields `null`. Static markers use these reviewed coordinates directly without Places retrieval; they are not automatically refreshed. A non-cafe marker appears when the map's cafe-only filter is turned off.
- Set `source.url` to the source used to check the entered facts and `source.reviewedAt` to the actual UTC review time (`YYYY-MM-DDTHH:mm:ssZ`). Do not invent values or dates. No enrichment calls are made when this form is filled or loaded.

Then run `npm run validate:data` from `app/`, commit the completed record to the submission PR, and let the remaining checks pass before merging. Directory and reviewed-location edits require the next patch version after main; update the package and both lockfile version roots when needed. The form file at repository root is a reusable example and is not imported automatically. The existing [`roaster-template.json`](../roaster-template.json) remains available for business-field edits, but is not needed for a location/rating-only review. Leave the accepted legacy snapshot unchanged.

## Review procedure

1. Search both collections by normalized website and name before adding a business. HTTP/HTTPS, leading `www`, fragments and trailing slashes share an identity; distinct paths, queries and ports remain distinct. A possible same-domain business needs manual review, rather than automatic merging. Separate brands on a shared platform can remain separate records.
   Form proposals recognise distinct Instagram profile paths as separate businesses. Profile matching ignores account casing and tracking queries, including previous website aliases; duplicate profiles are skipped. Instagram platform pages/posts and other same-domain websites still require manual review when that domain is already listed.
2. Assign an unused `biz-…` ID once for a new business and retain it through all corrections/reclassifications. Form recommendations use `biz-form-<submission-id>`. Keep known previous websites in `websiteAliases`; aliases remain reserved to that business and help identify later corrections. Aliases must have distinct normalized identities.
3. Keep roasters in `coffee-roasters.json` and sellers in `coffee-roasters-multi.json`. Use valid, nonrepeated AU states; `all` is available only to sellers. Subscription/selection/brew metadata belongs only to sellers and may remain absent when unverified.
4. Record the source of changed facts. Legacy records use `source: "legacy-directory", verifiedAt: null`. Community proposals record their public receipt and proposal time, with verification explicitly unknown. Operator reviews record a URL, actual `reviewedAt` and the `fields` independently checked; a state review does not verify every other field.
5. Review a branch's identity, state and public cafe access against operator information or independent submissions. Reuse an existing location/place identity when available; assign an unused `loc-…` ID only for a new branch. Existing accepted IDs live in the association manifest; reviewed overrides must reuse their location ID. Preserve existing place IDs through business corrections. Do not treat an Australian Google response as proof of business identity.
6. From `app/`, run `npm run validate:data`, `npm run check`, `npm test` and `npm run build`; run browser checks for changes affecting browsing. Review all related files together in one PR. GitHub rejects invalid identities, references, source metadata, website duplicates and collection classification. The same data validation also runs before every production build.

Deletion needs an explicit review of location references and website aliases; removing a referenced business causes validation to fail. The validator checks that every accepted legacy marker still has a location identity. Runtime refreshes continue to reuse provider place IDs and do not change curated records or package versions.

Rebase older data PRs onto current main and retain the new IDs/provenance when resolving conflicts. An older new-listing proposal needs a business ID and valid provenance before its checks can pass; replay against current data to regenerate it if needed. Do not overwrite reviewed branch edits during recovery.
